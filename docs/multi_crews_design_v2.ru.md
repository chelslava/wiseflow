# Документация по системе Crews v2

> **Статус**: требует утверждения
> **Дата**: 2026-03-10
> **Область изменений**: crew/ → crews/, модель Template→Instance, расширенные обязанности HRBP

---

## 1. Мотивация проектирования

Текущая система (v1) — это модель Template=Instance 1:1: файлы в `crew/workspaces/<agent-id>/` копируются напрямую в `~/.openclaw/workspace-<agent-id>/`, и каждая рабочая область определяет одного активного агента.

Это приносит два ограничения:
- **Невозможность множественного инстанцирования**: один и тот же тип роли не может быть активирован в нескольких независимых экземплярах (напр., два агента по обслуживанию для двух продукт-лайн)
- **Связывание шаблона и экземпляра**: шаблон рабочей области и инстанс во время выполнения не могут развиваться независимо

Ключевое изменение в v2: **разделение Crew Template (шаблона) от Crew Instance (экземпляра)**.

---

## 2. Основные концепции

### 2.1 Crew Template (шаблон)

Шаблон — это **чертёж** Crew, определяющий возможности, характер, инструменты и workflow. Шаблоны хранятся в папке кода `crews/`.

Источники шаблонов:
- **Встроенные шаблоны** (built-in): поставляются с OFB, main / hrbp / it-engineer
- **Официальные шаблоны** (official): поддерживается командой OFB, постоянно дополняются (напр., customer-service, developer и др.)
- **Самодельные пользователем** (user-created): создаются пользователем через HRBP
- **Из маркетплейса** (marketplace): предполагается future загрузка из маркетплейса Crew

### 2.2 Crew Instance (экземпляр)

Экземпляр — это **запущенная форма** шаблона — реальный рабочий агент. При активации шаблона HRBP копирует файлы шаблона в рабочую область во время выполнения, регистрирует в openclaw.json, формируя независимый экземпляр.

Особенности экземпляра:
- **Уникальный идентификатор** (instance-id), указывается пользователем или предлагается HRBP
- **Независимая рабочая область** (`.openclaw/workspace-<instance-id>/`)
- **Независимая память** (MEMORY.md в workspace экземпляра, развивается независимо при работе)
- **Независимая привязка канала** (можно привязать разные Feishu Bot/другие каналы)
- **Настраиваемые навыки** (после инстанцирования можно добавлять/удалять навыки, не затрагивая шаблон)
- **Связь с ID шаблона** (записывает происхождение из шаблона, для уведомлений об обновлениях шаблона)

Один шаблон можно инстанцировать в несколько Crew, каждый полностью независим.

### 2.3 Built-in Crew (встроенные Crew)

Три системных Crew, имеющих особую защиту:

| ID | Роль | Особенности |
|----|------|-------------|
| `main` | Маршрутизатор + исполнитель на случай ошибок | Единственный в глобальном масштабе, не может быть удалён или инстанцирован несколько раз |
| `hrbp` | Менеджер жизненного цикла Crew | Единственный в глобальном масштабе, не может быть удалён или инстанцирован несколько раз |
| `it-engineer` | Системный администратор OFB | Единственный в глубоковом масштабе, не может быть удалён или инстанцирован несколько раз |

Жизненный цикл встроенных Crew:
- Включается автоматически скриптом установки (`setup-crew.sh`)
- **Не управляется HRBP** — HRBP не может удалять, отключать или инстанцировать их несколько раз
- HRBP может **просматривать** их состояние, но не может изменять их жизненный цикл
- Пользователи по-прежнему могут изменять их поведение путём редактирования файлов рабочей области вручную (операция L3)

### 2.4 Режимы маршрутизации

Все Crew (включая встроенные) поддерживают два режима маршрутизации:
- **Режим spawn (маршрутизация)**: пользовательские сообщения поступают в Main Agent, Main Agent перенаправляет через`sessions_spawn`
- **Прямая привязка**: Crew привязывается к независимому каналу (например, Feishu Bot), пользователь общается напрямую в соответствующем чате
- **Гибридный режим**: один и тот же Crew может одновременно поддерживать spawn и прямую привязку

Порядок Autonomy Ladder (L1/L2/L3) остаётся неизменным.

```

│       ├── hrbp-list/

├── it-engineer/                # [built-in] IT Engineer
│   └── SOUL.md ... HEARTBEAT.md
│
│   # ── Официальные шаблоны ──
├── customer-service/           # [official] Customer Service
│   └── SOUL.md ... HEARTBEAT.md
├── developer/                  # [official] Developer
│   └── SOUL.md ... HEARTBEAT.md
├── content-writer/             # [official] Content Writer
│   └── SOUL.md ... HEARTBEAT.md
├── market-analyst/             # [official] Market Analyst
│   └── SOUL.md ... HEARTBEAT.md
└── operations/                 # [official] Operations
    └── SOUL.md ... HEARTBEAT.md
```

**Изменения по сравнению с v1**:
- `crew/workspaces/<agent>/` → `crews/<template-id>/` (плоская структура, убрана промежуточная прослойка workspaces)
- `crew/role-templates/*.md` → обновлен до полного 8-файлового шаблона, объединён в один уровень `crews/`
- `crew/role-templates/_template/` → `crews/_template/` (оставлен пустой каркас)

### 3.2 Структура во время выполнения (~/.openclaw/)

```
~/.openclaw/
├── openclaw.json               # Конфигурация выполнения (экземпляры регистрации в agents.list[])
├── TEAM_DIRECTORY.md           # Адресная книга включённых экземпляров (автоматически генерируется скриптом, единый источник, все агенты читают напрямую)
├── workspace/                  # Рабочая область OpenClaw по умолчанию
├── workspace-main/             # Рабочая область экземпляра Main Agent
├── workspace-hrbp/             # Рабочая область экземпляра HRBP
├── workspace-it-engineer/      # Рабочая область экземпляра IT Engineer
├── workspace-cs-product-a/     # Рабочая область экземпляра Customer Service A (из шаблона customer-service)
├── workspace-cs-product-b/     # Рабочая область экземпляра Customer Service B (из шаблона customer-service)
├── hrbp-templates/             # Копии шаблонов (для справки HRBP во время выполнения)
└── archived/                   # Архивированные рабочие области отключённых экземпляров
```

## 4. Спецификация шаблона

### 4.1 Структура папок шаблона

Каждая папка шаблона содержит:

```
<template-id>/
├── SOUL.md                     # Определение роли, основные обязанности, уровень автономности
├── AGENTS.md                   # Определение workflow
├── MEMORY.md                   # Начальная память (после инстанцирования развивается независимо)
├── USER.md                     # Предположения о пользователе
├── IDENTITY.md                 # Имя, роль, характер
├── TOOLS.md                    # Описание доступных инструментов
├── HEARTBEAT.md                # Состояние здоровья (изначально пустой)
├── DENIED_SKILLS               # [опционально] Список блокируемых встроенных навыков
├── BUILTIN_SKILLS              # [опционально] Дополнительные bundled skills, рекомендованные для установки в экземпляре
└── skills/                     # [опционально] Специфичные для шаблона навыки
    └── <skill-name>/
        ├── SKILL.md
        └── scripts/
```

Стандартные соглашения:
- Не IT-шаблоны рекомендуют по умолчанию блокировать `github`, `gh-issues`, `coding-agent`
- Шаблон `it-engineer` по умолчанию не блокирует упомянутые выше三项
- Если экземпляру требуется исключение, можно напрямую отрегулировать `DENIED_SKILLS` внутри workspace экземпляра

### 4.3 Система уровней команд (Command Tier System)

Каждый шаблон объявляет уровень команд в разделе `## Уровень привилегий` в `SOUL.md`:

```markdown
## Уровень привилегий
command-tier: T2
```

**Четыре уровня определены** (см. `crews/shared/COMMAND_TIERS.md` для полного списка команд):

| Уровень | Имя | Политика выполнения | Подходящий Crew |
|---------|-----|---------------------|-----------------|
| T0 | read-only | `security: deny` — запрещены все команды shell | Customer service, content-writer, market-analyst |
| T1 | basic-shell | `security: allowlist` — белый список только чтения: `cat`, `ls`, `grep`, `ps`, `curl` (только GET) | Coordination, operations |
| T2 | dev-tools | `security: allowlist` — T1 + `git`, `npm`, `pnpm`, `node`, `python`, `cp`, `mv`, `mkdir`, `rm`, ... | Developer, hrbp |
| T3 | admin | `security: full` — неограниченный доступ к shell | IT Engineer |

**Механизм выполнения**: `setup-crew.sh` автоматически сопоставляет уровень с двухуровневой конфигурацией привилегий в OpenClaw:
1. `openclaw.json` → `agents.list[].tools.exec`: политика security/ask на основе агентов
2. `~/.openclaw/exec-approvals.json`: белый список команд на основе агентов (команды в белом списке T1/T2 решаются через `command -v` к бинарным путям)

Действует более строгий из двух. `ask` для всех уровней устанавливается в `off` (у каналов, таких как Feishu, отсутствует UI для реального одобрения).

**Тонкая настройка**: если требуется добавить или заблокировать команды сверх базового уровня, создайте файл `ALLOWED_COMMANDS` в директории шаблона:
- `+<command>` — добавить разрешение на базу текущего уровня
- `-<command>` — заблокировать на базе текущего уровня

## 5. Управление экземплярами

### 5.1 Процесс инстанцирования

```
Потребность пользователя → Понимание намерения HRBP → Сопоставление/создание шаблона → Инстанцирование → Регистрация → Опциональная привязка канала
```

Пошаговые действия:
1. **Понимание намерения**: HRBP понимает, какой тип Crew требуется пользователю
2. **Сопоставление шаблона**: поиск index.md, нахождение лучшего совпадения
   - Найден → перейти в процесс инстанцирования
   - Не найден → помочь пользователю создать новый шаблон (сначала загрузить в crews/, обновить index.md), затем инстанцировать
3. **Настройка инстанцирования** (подтверждение пользователя, L3):
   - **ID экземпляра**:指定 пользователем или предложенный HRBP (напр., `cs-product-a`)
   - **Название экземпляра**:指定 пользователем (напр., "Клиентский сервис продукта A")
   - **Привязка канала**: требуется ли привязать независимый канал? К какой?
   - **Настройка навыков**: требуется ли дополнительный навык или блокировка определённых навыков?
   - **Тонкая настройка роли**: требуется ли изменить описание роли в SOUL.md?
4. **Выполнение инстанцирования**:
   - Скопировать файлы шаблона в `~/.openclaw/workspace-<instance-id>/`
   - Скопировать протоколы `shared/` в рабочую область экземпляра
   - Если есть специфичные для шаблона навыки, установить в `skills/` рабочей области экземпляра
   - Изменить файлы рабочей области экземпляра в соответствии с пользовательскими настройками
5. **Регистрация экземпляра**:
   - Добавить запись в `agents.list[]` в `openclaw.json` (используются только нативные поля верхнего уровня)
   - Если есть привязка канала, добавить запись `bindings[]`
   - Вычислить список фильтрации навыков (если есть DENIED_SKILLS)
   - Записать отношение экземпляр→шаблон в MEMORY.md HRBP
6. **Обновление адресной книги Main Agent**: добавить новую запись экземпляра в MEMORY.md Main Agent
7. **Завершение**: сообщить результат создания экземпляра, напомнить о перезапуске Gateway

### 5.2 Пример сценария с несколькими экземплярами

Пользователь: "Мне нужны два агента по обслуживанию клиентов: один для продукта A, другой для продукта B,分别 привязаны к разным группам Feishu."

HRBP выполняет:
```
Шаблон: customer-service
Экземпляр 1: cs-product-a
  - workspace: ~/.openclaw/workspace-cs-product-a/
  - SOUL.md: отрегулирован на "Клиентский сервис продукта A", внедрить знания продукта A
  - MEMORY.md: независимая память
  - channel: feishu:product-a-bot
Экземпляр 2: cs-product-b
  - workspace: ~/.openclaw/workspace-cs-product-b/
  - SOUL.md: отрегулирован на "Клиентский сервис продукта B", внедрить знания продукта B
  - MEMORY.md: независимая память
  - channel: feishu:product-b-bot
```

Оба экземпляра работают полностью независимо, общий для них только структурный каркас роли, но с различными знаниями, памятью и каналами.

### 5.3 Регистрация экземпляра в openclaw.json

Запись agent в openclaw.json **использует только нативные поля верхнего уровня**, не делая никаких кастомных расширений:

```jsonc
{
  "agents": {
    "list": [
      {
        "id": "main",
        "name": "Main Agent",
        "workspace": "workspace-main"
      },
      {
        "id": "cs-product-a",
        "name": "Клиентский сервис продукта A",
        "workspace": "workspace-cs-product-a",
        "subagents": ["main"]
      },
      {
        "id": "cs-product-b",
        "name": "Клиентский сервис продукта B",
        "workspace": "workspace-cs-product-b",
        "subagents": ["main"]
      }
    ]
  }
}
```

**Отслеживание связи шаблон-экземпляр** не осуществляется в openclaw.json, а поддерживается HRBP в своем MEMORY.md:

```markdown
## Реестр экземпляров

| ID экземпляра | Template | Дата создания | Примечание |
|---------------|----------|---------------|------------|
| cs-product-a | customer-service | 2026-03-10 | Клиентский сервис продукта A |
| cs-product-b | customer-service | 2026-03-10 | Клиентский сервис продукта B |
```

**Глобальный список защиты** жёстко запрограммирован в SOUL.md HRBP и скриптах (`main`, `hrbp`, `it-engineer`) и не требует конфигурационных меток.

### 5.4 Жизненный цикл экземпляра

```
Создание (HRBP recruit) → Работающий → Изменение (HRBP modify) → Отключение (HRBP remove → Архивирование)
                                                         ↓
                                               ~/.openclaw/archived/<instance-id>/
```

Отключение не означает удаление шаблона — шаблон остаётся в `crews/` и может быть снова инстанцирован в любое время.

## 6. Расширенные обязанности HRBP

### 6.1 Изменения от v1 к v2

| Обязанность | v1 | v2 |
|-------------|----|----|
| Recruitment | По справочнику role-templates создание workspace непосредственно | Сначала сопоставление/создание **шаблона**, затем **инстанцирование** |
| Transfer | Редактирование файлов workspace | Редактирование файлов workspace **экземпляра** (не затрагивает шаблон) |
|Dismiss | Удаление agent, архивирование workspace | Отключение **экземпляра**, архивирование workspace (шаблон сохраняется) |
| Адресная книга | Поддержка Main Agent MEMORY.md | Поддержка Main Agent MEMORY.md + `crews/index.md` |
| Новая: Управление шаблоном | — | Создание/обновление/удаление шаблонов, поддержка index.md |
| Новая: Обновление шаблона | — | Обнаружение обновлений шаблона, уведомление соответствующих экземпляров |

### 6.2 Новые процессы работы HRBP

**Процесс создания шаблона**:
1. Понимание потребностей пользователя (роль, возможности, инструменты, стиль)
2. Проверка наличия reused существующего шаблона
3. Создание нового шаблона на основе `_template/` или ближайшего существующего
4. Запись нового шаблона в `crews/<template-id>/`
5. Обновление `crews/index.md`
6. Вход в процесс инстанцирования

**Запрос списка шаблонов**:
- HRBP может читать `crews/index.md` для понимания всех доступных шаблонов
- Представление списка шаблонов и их кратких описаний пользователю
- Помощь пользователю в выборе наиболее подходящего шаблона

### 6.3 Границы защиты

HRBP **не может**:
- Удалять или отключать встроенные Crew (main / hrbp / it-engineer)
- Создавать несколько экземпляров встроенных Crew

HRBP **может**:
- Просматривать состояние и конфигурацию встроенных Crew
- Управлять полным жизненным циклом всех не встроенных экземпляров
- Управлять всеми шаблонами (включая просмотр встроенных шаблонов, создание/удаление/редактирование не встроенных шаблонов)

## 7. Интеграция Addon

### 7.1 Addon предоставляет шаблоны Crew

Addon может предоставлять шаблоны Crew в своей директории `crew/` (обратите внимание: внутри addon по-прежнему используется путь `crew/`, отличный от `crews/` основного проекта):

```
addons/<addon-name>/
├── crew/                       # Шаблоны Crew, предоставленные Addon
│   └── <template-id>/
│       ├── SOUL.md ... HEARTBEAT.md
│       └── skills/             # Специфичные для шаблона навыки
└── skills/                     # Глобальные навыки, предоставленные Addon
```

### 7.2 Процесс загрузки шаблонов addon

`apply-addons.sh` обрабатывает шаблоны Crew в addon:
1. Скопировать шаблоны в `crews/<template-id>/` (в кодовой базе, для использования HRBP)
2. Обновить `crews/index.md`, пометить источник как этот addon
3. **Не автоматически инстанцировать** — требуется запустить пользователя через HRBP
4. Если addon указывает `auto-activate: true`, то `apply-addons.sh` автоматически инстанцирует

## 8. Изменения setup-crew.sh

### 8.1 Новое поведение

```bash
./scripts/setup-crew.sh
```

1. **Установка встроенных шаблонов**: скопировать рабочие файлы из `crews/main/`, `crews/hrbp/`, `crews/it-engineer/` во время выполнения
2. **Автоматическое инстанцирование встроенных Crew**: три встроенных Crew по умолчанию включены, зарегистрированы в `openclaw.json`
3. **Копирование общих протоколов**: `crews/shared/` → рабочие области каждого активного экземпляра

## Обновление v3: Система типов внутренних и внешних crew (2026-03)

> Статус: Внедрено
> Область изменений: Разделение типов crew, обновление структуры директорий, передача прав на управление жизненным циклом

### 3.0 Мотивация проектирования

В v2 система crews объединяла все crew под управлением (HRBP управлял всеми crew). В v3 введено разделение на "внутренние crew" и "внешние crew" для лучшего соответствия реальным бизнес-сценариям:

- **Внутренние crew**: обслуживают внутренних менеджеров, технически возможны маршрутизация через Main Agent (spawn + bind), могут обновляться автономно
- **Внешние crew**: обслуживают внешних клиентов, доступны только через прямой канал (bind-only), ограничены привилегиями, не могут обновляться автономно

### 3.1 Типы crew

См. `crews/shared/CREW_TYPES.md` (авторитетный документ определения).

| Тип | Представитель | Режим навыков | Маршрутизация | Жизненный цикл | Обновление |
|-----|---------------|--------------|--------------|--------------|------------|
| internal | main/hrbp/it-engineer | inherit (наследование) | spawn+bind | Main Agent | Инициатор — менеджер |
| external | customer-service | declare (декларативный) | bind-only | HRBP | Инициатор — HRBP |

### 3.2 Изменение структуры директорий

```
~/.openclaw/
├── crew_templates/       # Шаблоны для внутренних crew (доступ Main Agent)
│   ├── TEAM_DIRECTORY.md # Адресная книга для внутренних crew (автоматическая генерация)
│   ├── main/
│   ├── hrbp/
│   └── it-engineer/
├── hrbp_templates/       # Шаблоны для внешних crew (доступ HRBP)
│   ├── index.md
│   ├── customer-service/
│   └── _template/
├── workspace-hrbp/
│   └── EXTERNAL_CREW_REGISTRY.md  # Реестр экземпляров внешних crew (только HRBP)
...
```

### 3.3 Передача прав на управление жизненным циклом

| Операция | v2 (HRBP единое управление) | v3 (разделение обязанностей) |
|----------|-----------------------------|------------------------------|
| recruit/dismiss для внутренних crew | HRBP | **Main Agent** (навыки crew-recruit/crew-dismiss) |
| recruit/dismiss для внешних crew | HRBP | HRBP (навыки hrbp-recruit/hrbp-remove)|
| upgrade для внешних crew | — | HRBP (навык hrbp-feedback-review + поток upgrade)|
| upgrade для внешних crew | Управление HRBP | Инициатор upgrade — HRBP |

### 3.4 Увеличение привилегий Main Agent

Main Agent от T1 → **T2**, получает возможность выполнять скрипты управления crew.

Новые навыки:
- `crew-list`: просмотр адресной книги внутренних crew
- `crew-recruit`: регистрация нового внутреннего crew (вызов add-agent.sh --crew-type internal)
- `crew-dismiss`: отключение внутреннего crew (вызов remove-agent.sh)

### 3.5 Увеличение привилегий HRBP

HRBP от T2 → **T3**, сосредоточено на управлении внешними crew.

Улучшения:
- Встроенная OFB знание системы (адреса документации, локальные пути)
- Новый навык `hrbp-feedback-review`: сканирование пользовательских отзывов внешних crew, разработка плана upgrade
- Поддержка `EXTERNAL_CREW_REGISTRY.md` (авторитетная запись экземпляров внешних crew)

### 3.6 Упрощение официальных шаблонов

Сохранены только 4 официальных шаблона:
- **Внутренние**: main, hrbp, it-engineer
- **Внешние**: customer-service

Удалены: developer, content-writer, market-analyst, operations (могут быть созданы пользователем по желанию через HRBP)

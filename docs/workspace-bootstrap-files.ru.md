# Механизм Bootstrap файлов рабочей области

> Базовая версия: openclaw v2026.4.11

В каждой рабочей директории crew (`~/.openclaw/workspace-<id>/`) хранится несколько файлов Markdown, которые openclaw inject-ит в системный промпт при каждом запуске агента, тем самым влияя на поведение, личность и память агента. В этом документе описаны назначение каждого файла, время их загрузки и расширения wiseflow поверх стандартного механизма.

---

## I. Стандартные Bootstrap файлы (родные openclaw)

openclaw распознаёт 8 стандартных файлов, которые **загружаются в следующем порядке внутрь системного промпта**:

| № | Имя файла | Краткое описание | Источник содержимого |
|---|----------|------------------|----------------------|
| 1 | `AGENTS.md` | Общие правила рабочей области: процесс запуска сессии, стратегии управления памятью, «красные линии» безопасности, форматы платформ, поведение heartbeat и т.д. | Фреймворк автоматически создаёт шаблоны, **настраивает пользователь (или crew template)** |
| 2 | `SOUL.md` | Ядро личности агента: ценности, правила поведения, стиль работы, определение границ | Фреймворк создаёт шаблон, **настраивает пользователь (или crew template)** |
| 3 | `TOOLS.md` | Буферная память о конфигурации локальных инструментов: псевдонимы камер, имена SSH-хостов, предпочтительные тональности TTS и т.д. — SKILL.md определяет «как это использовать», а TOOLS.md фиксирует «что именно в вашей среде» | Фреймворк создаёт пустой шаблон, **обслуживается пользователем во время выполнения** |
| 4 | `IDENTITY.md` | Служебная карточка агента: имя, визуальный образ (AI/робот/другое), темперамент, уникальный emoji и путь к аватару | Фреймворк создаёт шаблон, **подтверждается агентом и пользователем при первом bootstrap** |
| 5 | `USER.md` | Информация о пользователе: имя/обращение, часовой пояс, предпочтения, заметки о контексте | Фреймворк создаёт шаблон, **заполняется агентом при первом bootstrap** |
| 6 | `HEARTBEAT.md` | Список периодических задач heartbeat: агент выполняет эти проверки по таймеру heartbeat | Фреймворк создаёт пустой шаблон, **обслуживается агентом во время работы** |
| 7 | `BOOTSTRAP.md` |ceremony — пошаговое руководство для первого запуска: помогает агенту определить себя, познакомиться с пользователем, выбрать канал подключения (**файл однократного использования**) | Фреймворк создаёт автоматически, **удаляется после завершения первого запуска агентом** |
| 8 | `MEMORY.md` | Долгосрочная память: важная информация, сохраняемая между сессиями (загружается только в главной сессии, для защиты конфиденциальности от групповых бесед/под-агентов) | **Создаётся и обслуживается пользователем/агентом самостоятельно**, изначально не существует |

> `memory.md` (в нижнем регистре) — резервное имя для `MEMORY.md`, при одновременном присутствии обоих файлов приоритет отдаётся `MEMORY.md`.

## II. Время загрузки и правила фильтрации

### 2.1 Главная сессия (диалог, инициированный непосредственно пользователем)

Загружаются **все 8 файлов** (если они существуют).

### 2.2 Под-агентовая сессия (subagent, запущенный через `sessions_spawn`) и Cron-сессии

Загружаются **минимальный набор файлов**, чтобы сэкономить token:

| Файл | Загружается |
|------|------------|
| AGENTS.md | ✓ |
| SOUL.md | ✓ |
| TOOLS.md | ✓ |
| IDENTITY.md | ✓ |
| USER.md | ✓ |
| HEARTBEAT.md | ✗ (исключён) |
| BOOTSTRAP.md | ✗ (исключён) |
| MEMORY.md | ✗ (исключён, чтобы избежать утечки конфиденциальной информации) |

### 2.3 Heartbeat-сессии (периодические проверки по таймеру heartbeat)

На базе минимального набора файлов **дополнительно загружается HEARTBEAT.md**, но только в случае, если этот agent является назначенным по умолчанию agent с heartbeat.

Если у вас включено `heartbeat.lightContext: true`, то heartbeat-сессии загружают только `HEARTBEAT.md`, остальные файлы полностью исключаются (максимальная экономия token).

### 2.4 Оптимизация continuation-skip

Когда `agents.defaults.contextInjection = "continuation-skip"` (не значение по умолчанию), после завершения первого bootstrapа в последующих сессиях инъекция файлов пропускается, чтобы снизить частоту недействительности кэша промпта. Значение по умолчанию `"always"` означает инъекцию при каждом туре.

## III. Ограничения по размеру

| Параметр ограничения | Значение по умолчанию | Ключ конфигурации |
|----------------------|----------------------|------------------|
| Максимальный объём диска для чтения одного файла | 2 МБ | жёстко задан в коде |
| Максимальное количество символов, инжектированное из одного файла | 20 000 символов | `agents.defaults.bootstrapMaxChars` |
| Общий максимальный объём всех файлов | 150 000 символов | `agents.defaults.bootstrapTotalMaxChars` |

Если объём файла превышает допустимый лимит, содержимое обрезается, а агент получает предупреждение в зависимости от конфигурации `bootstrapPromptTruncationWarning`.

## IV. Жизненный цикл BOOTSTRAP.md

1. **При первом развёртывании**:框架 автоматически создаёт `BOOTSTRAP.md`, записывая состояние в `.openclaw/workspace-state.json`
2. **Первый диалог**: агент читает `BOOTSTRAP.md`, подтверждает свою личность с пользователем (имя, характер, подключение каналов), обновляя тем самым `IDENTITY.md`, `USER.md`, `SOUL.md`
3. **завершение ceremony**: агент **удаляет** `BOOTSTRAP.md`, framework устанавливает `setupCompletedAt` в текущую дату во `файле workspace-state.json`
4. **Последующая работа**: `BOOTSTRAP.md` больше не существует, framework не пересоздаёт его

## V. Правила безопасности MEMORY.md

`MEMORY.md` загружается **только в главной сессии** (диалог пользователь-агент один-на-один), **не инжектируется** в групповые сессии, сессии sub-agents или cron-сессии. Это сделано для предотвращения раскрытия конфиденциальной персональной информации в открытых средах (например, Discord-группы, Telegram-каналы с несколькими участниками).

Агент должен чётко фиксировать это правило в `AGENTS.md`:

```markdown
### 🧠 MEMORY.md — Долгосрочная память
- **Загружается только в главной сессии (прямой диалог 1-на-1 с пользователем)**
- **Не загружается в групповых чатах, sub-agent сессиях или внешних диалогах** (изоляция безопасности)
```

## VI. Расширения wiseflow (не часть openclaw)

Следующие файлы — расширения wiseflow по договорённости, **openclaw framework их не обрабатывает автоматически**, они читаются скриптами или агентом и then записываются в `openclaw.json`.

### 6.1 DECLARED_SKILLS — белый список внешних crew-навыков

| Параметр | Описание |
|----------|----------|
| Применение к crew-типу | Внешние crew (T0, например sales-cs) |
| Назначение | Задаёт навыки, которые этот crew **имеет право использовать**, только перечисленные навыки доступны |
| Используется | `add-agent.sh` (под капотом в скрипте hrbp-recruit) считывает и записывает в `agents.list[].skills` конкретного агента |
| Формат | На каждой строке по одному навыку, комментарии начинаются с `#` |

Внешние crew используют принцип минимальных привилегий: не наследуют базовые глобальные навыки, могут использовать только те, которые явно перечислены в `DECLARED_SKILLS`. Это предотвращает случайный доступ агентов, обслуживающих внешних клиентов, к внутренним инструментам.

### 6.2 BUILTIN_SKILLS — расширение внутренних crew навыками

| Параметр | Описание |
|----------|----------|
| Применение к crew-типу | Внутренние crew (T1/T2, например selfmedia-operator, business-developer, designer) |
| Назначение | Перечисляет дополнительные навыки, требуемые для конкретного crew поверх общей базы |
| Используется | `setup-crew.sh` (начальная установка/обновление) или `recruit-internal-crew.sh` (Main Agent при.recruit-ит нового внутреннего crew) считывает и объединяет с общей базой, затем записывает в `agents.list[].skills` |
| Формат | По одному навыку на строку, не нужно повторять навыки, уже входящие в общую базу |

**Общая база** (навыки, общие для всех внутренних crew) определяется в конфигурациях агентов из `config-templates/openclaw.json` и обычно включает: `nano-pdf`, `skill-creator`, `session-logs`, `tmux`, `weather`, `summarize`, `self-improving` и т.д.

### 6.3 DENIED_SKILLS — исключение навыков

| Параметр | Описание |
|----------|----------|
| Применение | Все crew |
| Назначение | Явно исключает из списка допустимых навыков, чтобы предотвратить некорректное конфигурирование |
| Используется | `add-agent.sh` удаляет навыки из этого списка при формировании `agents.list[].skills` |
| Типичное применение | Исключает `github`/`gh-issues`/`coding-agent` (специфичные для IT), навыки, предназначенные для конкретных бизнес-разработчиков и т.д. |

### 6.4 ALLOWED_COMMANDS — точечное разрешение команд

| Параметр | Описание |
|----------|----------|
| Применение | Внешние crew (T0) |
| Назначение | На основе T0 (по умолчанию — блокировка всех shell-команд) разрешает конкретные пути к скриптам |
| Формат | `+<путь относительно workspace>` |
| Типичное применение | Разрешение `./skills/customer-db/scripts/*.sh`, `./skills/payment_send/scripts/*.sh` и другие декларативные скрипты навыков |

## VIII. Самопроверка Crew

При инстанцировании или отладке crew проверьте следующее:

- [ ] Есть ли в `AGENTS.md` чёткий процесс запуска сессии (чтение SOUL.md, USER.md, MEMORY.md и т.д.)?
- [ ] Установлен ли в `SOUL.md` правильный `crew-type` (`internal` или `external`)?
- [ ] Заполнен ли (или содержит ли инструкции по заполнению) `IDENTITY.md`?
- [ ] Содержит ли `HEARTBEAT.md` только необходимые периодические задачи (должен быть кратким и точным, чтобы не тратить token впустую)?
- [ ] Является ли `BOOTSTRAP.md` одноразовым файлом и удаляется ли он после первого запуска?
- [ ] Существует ли `DECLARED_SKILLS` и полон ли его список для внешних crew?
- [ ] Включает ли `BUILTIN_SKILLS` для внутренних crew все специфичные навыки (не включая навыки из общей базы)?
- [ ] Исключает ли `DENIED_SKILLS` неподходящие для данного crew глобальные навыки?
- [ ] Для внешних crew: разрешает ли `ALLOWED_COMMANDS` только скрипты, требуемые декларативными навыками?

# Соглашения и определения awada

Awada — это CUI (conversational user interface), созданный для приложений на основе LLM, цель которого — превратить демо-проекты на основе LLM в готовые к эксплуатации продукты.

Awada включает три основных модуля: awada server, redis infrastructure, awada bot.

Следующие концепции и соглашения применяются в системе awada:

#### Каналы сообщений

Канал сообщений — это внешний канал связи, например, API客服 WeChat, API Feishu, API Tiny Group WeChat, API企微, API стороннего шлюза WeChat и т.д.

В системе awada каналы сообщений полностью управляются awada server, awada bot не интересуется источником сообщений и куда они будут отправлены после обработки...

- **В версии awada 1.x один экземпляр server может подключаться к нескольким каналам, но один канал может подключаться только к одному экземпляру server**

### События сообщений

Основной элемент обмена данными между awada server и awada bot — это события сообщений ( MSG Event),简称 "события"（MSG Event）.

В цифровом виде событие сообщения представляет собой dict определенного формата, соглашение о формате см. во второй части (в конце документа).

#### Очереди событий сообщений

События сообщений передаются между awada server и awada bot через очереди событий (Stream）.

В версии awada 1.x очереди событий поддерживаются с помощью redis infrastructure.

#### Линии (lanes) событий сообщений

Возьмем яркий пример: высокоскоростная железная дорога Шанхай-Пекин называется "линией", но это не одна железная дорога, а две двухнаправленные железные дороги. То же происходит и с автомобильными дорогами: в основном двухполосные дороги, четырехполосные и даже восьми- или десятиполосные на автострадах...

Таким образом, в производственной среде очереди событий (stream) не могут существовать изолированно, они всегда появляются группами; эта группа stream называется lane.

Она представляет определенную линию связи, такую как между пользователем и ботом, между администратором и ботом, между определенным пользователем и ботом для конкретного маркетингового мероприятия...

В версии awada 1.x один lane содержит 4 stream, их назначение и правила именования таковы:

- Входящие события (запись server, чтение bot）:

  `awada:events:inbound:{lane}`

- Исходящие события (запись bot, чтение server）:

  `awada:events:outbound:{lane}`

- Очередь сбоев обработки (запись bot, чтение bot）:

  `awada:events:bot_failed:{lane}`

- Очередь сбоев отправки (запись server, чтение server）:

  `awada:events:send_failed:{lane}`

Правила именования должны строго соблюдаться, поскольку это единственный способ связать определенный экземпляр server и экземпляр bot (в версии awada 1.x）.

- **В версии awada 1.x один экземпляр server может подключаться к нескольким линиям (lane), на одной линии может быть несколько bot, но один экземпляр bot может подключаться только к одной линии**
- **Правила доставки server настолько гибкие, что можно полностью настраивать, например, доставлять групповой чат на одной линии на отдельную lane, а частные чаты — на другую lane**
- **Если server хочет сбросить диалог определенного пользователя, это можно сделать только путем назначения этому пользователю нового channel или tenant**

#### awada bot

Awada bot — это обработчик сообщений; в этом проекте awada 1.x разработан для высокой пропускной способности, поэтому допускается наличие нескольких awada bot, использующих одну конфигурацию, для обслуживания одной линии (lane), что называется группой bot, однако **bot, обслуживающие одну и ту же линию (lane), должны использовать одну и ту же конфигурацию**, то есть их конфигурации должны быть идентичными. **При更换 линии (lane) необходимо заменять конфигурацию bot, даже если это тот же тип bot.**

Например:

lane1 для линии обслуживания продукта 1, lane2 для линии обслуживания продукта 2, два bot на этих line должны иметь разную конфигурацию. Это означает, что разные line требуют разных "типов" bot.

Поскольку в версии awada 1.x в качестве уникального идентификатора сеанса используется строковое значение `{platform}:{user_id_external}:{channel_id}:{tenant_id}`, если bot для lane1 и lane2 используют одну и ту же конфигурацию, может возникнуть проблема нарушения изоляции сеансов, то есть bot не сможет получить точный контекст текущего диалога пользователя.

### Сводка концепций

Если "объединить" вышеуказанные концепции, их логическая связь будет следующей:

```
[Пользователи различных платформ] -> (каналы сообщений) -> [Awada Server] -> (awada:events:inbound:{lane}) -> [Группа Awada Bot]
                                                                                          |
                                                                                      (обработка & генерация)
                                                                                          |
[Пользователи различных платформ] <- (каналы сообщений) <- [Awada Server] <- (awada:events:outbound:{lane}) <- [Группа Awada Bot]
```

Более наглядным сравнением все же является железная дорога:

- awada server: железнодорожный вокзал
- lane: железнодорожная линия (stream — это конкретные рельсы）
- awada bot: поезда, бегущие по линии
- MSG Event: пассажиры
- Каналы сообщений: входы и выходы на железнодорожном вокзале

Если необходимо в группе @определенному пользователю, action_ask - [0, ["string", ...]], последующий массив - список ID пользователей, которые нужно @,其中"all"означает всех пользователей（@реализация на стороне server, поскольку API различных каналов могут иметь разные соглашения）；

## 1. Жизненный цикл inbound-сообщений

При записи сообщения в inbound stream **TTL (время жизни) должно быть 24 часа**.

### Реализация

Используйте команду `XTRIM` Redis Stream в сочетании с параметром `MINID` или задачу периодической очистки при `XADD`:

```typescript
// Пример: очистка сообщений за последние 24 часа
const minId = Date.now() - 24 * 60 * 60 * 1000;
await redis.xtrim(streamKey, 'MINID', '~', `${minId}-0`);
```

## 2. Определение ключа сеанса (важно)

### Что такое ключ сеанса

Ключ сеанса используется для уникальной идентификации контекста диалога;
```
Session Key = {platform}:{user_id_external}:{channel_id}:{tenant_id}
```

### Назначение ключа сеанса

| Назначение | Описание |
|------|------|
| **Блокировка сеанса** | Предотвращает параллельную обработку сообщений одного сеанса, обеспечивает порядок диалога |
| **Имя диалога** | Используется как name Conversation, удобно для управления |
| **Хранение Conversation ID** | Используется как Redis key для хранения Coze conversation_id |

### Обязательные поля

При записи сервером сообщений **обязательно должны иметь значения следующие поля**:

| Поле | Описание | Пример |
|------|------|------|
| `meta.platform` | Платформа источника сообщения | `wechat`, `telegram`, `web` |
| `meta.user_id_external` | Уникальный идентификатор пользователя на платформе | `wx_user_123`, `tg_456` |
| `meta.channel_id` | Идентификатор канала/группы | `001`, `group_abc` |
| `meta.tenant_id` | Идентификатор арендатора | `default`, `customer_xyz` |

### Очистка истории диалога

⚠️ **Важно**: При необходимости сброса истории диалога пользователя это можно сделать **только путем изменения `tenant_id`**.

```typescript
// Пример: очистка истории диалога пользователя
// До: tenant_id = "0"
// После: tenant_id = "1" или "20241216"
```

## 3. Соглашение по полям inbound-сообщений

### Поле type

В настоящее время awada-bot обрабатывает ответы только для событий типа `"MESSAGE_NEW"`, остальные типы зарезервированы или используются для внутреннего обмена данными между программами.

### Специальные поля Bot (не заполнять server)

Следующие поля автоматически заполняются awada-bot в процессе обработки для механизмов повторных попыток. **Server при заполнении не должен заполнять или не передавать**:

| Поле | Описание | Server | Bot |
|------|------|-----------|--------|
| `meta.conversation_id` | openclaw session_id | **не заполнять** | Автоматическое заполнение |
| `meta.chat_id` | openclaw chat_id | **не заполнять** | Автоматическое заполнение |

### Пример

```json
{
  "event_id": "evt_123",
  "type": "MESSAGE_NEW",
  "timestamp": 1702694400,
  "meta": {
    "platform": "wechat",
    "tenant_id": "default",
    "channel_id": "001",
    "lane": "user",
    "user_id_external": "wx_user_123"
  },
  "payload": [{
    "type": "text",
    "text": "Привет"
  },
  {
    "type": "image",
    "file_url": "https://example.com/image.png"
  },
  {
    "type": "audio",
    "file_path": "/path/to/audio.mp3"
  },
  {
    "type": "file",
    "file_id": "dddddxxxxxxxxx"
  }]
}
```

> ⚠️ Обратите внимание: поля `conversation_id` и `chat_id` не должны появляться в исходном сообщении, Bot будет автоматически заполнять их в процессе обработки.

## 4. Гарантия порядка сообщений

### Обязанности server

1. **Запись по порядку**: Сообщения одного пользователя должны записываться в Redis Stream в порядке получения
2. **Запись без параллелизма**: Избегать параллельной записи сообщений одного пользователя, чтобы не нарушать порядок

### Гарантия Bot

Bot гарантирует последовательную обработку одного и того же ключа сеанса с помощью механизма блокировки сеанса, не требует дополнительной обработки со стороны Server.

## 6. Соглашение о режиссуре

Сообщения, удовлетворяющие одновременно двум условиям, считаются режиссерскими инструкциями:

- 1. Отправитель в списке режиссеров (по соглашению {platform}:{user_id_external}:{channel_id}:{tenant_id}，其中tenant_id можно определить как специальный id，например，999，для различия диалога режиссера как обычного пользователя）；
- 2. Сообщение является чистым текстом и начинается с `/"例如"` `/ding`, `/auto_sale_and_delivery`.

Для следующих инструкций режиссера, требующих немедленного отклика, следует обрабатывать на стороне server без помещения в очередь событий.

В настоящее время инструкции режиссера, требующие немедленного отклика, включают:

- /ding

Другие инструкции режиссера поступают в очередь событий admin lane как события "MESSAGE_NEW" для обработки bot.

Обратите внимание：bot не требует аутентификации и различия личности, все сообщения в канале admin считаются режиссерскими инструкциями。

## Инфраструктура Redis

Lane и stream в awada 1.x реализованы с помощью redis (7.x），核心的 дизайнерская концепция:

**"Redis Streams + Inbound/Outbound архитектура, управляемая событиями (EDA) + Inbound/Outbound model"** 

- **Семантика доставки (по умолчанию)**：Redis Streams + Consumer Group => **At-least-once** (возможны повторные доставки）
- Все Consumer（Bot/Server dispatcher）должны выполнять **уникальность** или **дедупликацию** по `event_id`

#### Уникальность / Дедупликация (обязательна для At-least-once）

- **Bot потребляет Inbound**：использует `event_id` в качестве ключа уникальности (рекомендуется `SETNX processed:{event_id} 1 EX <ttl>` Redis）
- **Server потребляет Outbound**：использует `event_id` в качестве ключа уникальности (предотвращает повторную отправку на платформу）
- **Связь**：Outbound должен указывать `reply_to_event_id`, для отслеживания замкнутого цикла "вопрос-ответ"

#### Время ACK (жестко определено）

- Bot：**(1) Завершить обработку (2) Успешно записать в Outbound (3) Успешно отправить курсор сеанса (см. 3.3）后**再 ACK Inbound
- Server：**Успешный вызов API платформы (получение успешного ответа）后**再 ACK Outbound

Такой подход гарантирует "результаты не теряются", но вводит дублирование, для чего необходима компенсация через уникальность (разумно）。

#### Распределенная блокировка

В основном для bot для обеспечения отсутствия параллелизма одного и того же сеанса (предотвращает нарушение порядка сообщений）

#### Общее хранилище

Для хранения общих полей используется очередь kv redis, позволяя server и bot быть бессостоятельными, удовлетворяя потребностям распределенного развертывания。

## Основные функции Server

### Базовая функция: "переводчик" (Adapter）：

  * **Inbound (входящий）:** Все входящие внешние запросы, Server в первую очередь очищает, преобразует их в **единый внутренний формат событий** (payload по фиксированному протоколу, см. 3.1.1），пишет в Redis Streams `awada:events:inbound:{lane}`。Bot должен понимать только этот формат и подписываться на соответствующий stream в lane, за который он отвечает。
  * **Outbound (исходящий）:** После обработки Bot генерирует **единое событие ответа** (payload также по фиксированному протоколу, см. 3.1.1），пишет в Redis Streams `awada:events:outbound:{lane}`。Server после обнаружения преобразует ее на основе поля `platform` в формат API WeChat или Telegram для отправки。

### Определение идентичности пользователя

Идентификация пользователя происходит на стороне server, и результат используется для определения доставки в разные lane。

**bot не определяет личность пользователя, он определяет только lane**

### Режиссерские инструкции первого уровня

Инструкции, посланные режиссерами и не требующие обработки bot, только системные инструкции, должны начинаться с `/"，но не все`/" являются инструкциями первого уровня；в awada 1.x заключены инструкции первого уровня режиссера：：

- /ding ： Проверка эффективности системы, прямой ответ awada server xxx（ID экземпляра） reply dong at YYYY-MM-DD HH:MM:SS 

## Основные функции awada bot

### Механизм блокировки сеанса

Bot использует следующие структуры данных redis для управления сеансом：

| Формат ключа | Тип данных | Назначение | TTL |
|----------|----------|------|-----|
| `awada:session_lock:{session_key}` | String | Блокировка сеанса, предотвращает параллельную обработку | 16 минут |
| `awada:session_conv:{session_key}` | String | Хранит Coze conversation_id | Постоянно |

Несколько экземпляров bot, потребляющих сообщения, гарантируют последовательную обработку одного и того же ключа сеанса с помощью блокировки сеанса：

```
Bot1 читает msg1 (сессия A) → Получение блокировки успешно → Обработка → Выпуск блокировки
Bot2 читает msg2 → Блокировка занята → Ожидание (максимум 15 минут）
                              ↓
                    Блокировка выпущена → Успех получения → Обработка msg2 ✅ (правильный порядок）
                              ↓
                    15 минут истекло → Обработка ошибки (не повторно）
```

### Восстановление Pending（Восстановление после сбоя Worker）

- Перед сбоем bot（или внезапным выходом）bot преобразует уже полученные, но еще не обработанные сообщения в сиротскую очередь；
- Bot при каждом запуске должен регулярно сканировать Pending группы потребителей и использовать `XAUTOCLAIM` для восстановления истекших сообщений (рекомендуется согласование с повторной попыткой：`min_idle_time = 30s`)。

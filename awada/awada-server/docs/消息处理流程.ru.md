# Процесс обработки сообщений

> Данный документ описывает процесс обработки сообщений awada-server, который является переписанной версией wechaty с использованием qiweapi в качестве нижележащего протокола связи.

---

## 1. Сравнение архитектур

### 1.1 Старая архитектура (wechaty)

```
┌─────────────────────────────────────────────────────────┐
│                    SDK wechaty                          │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐          │
│  │  scan    │    │  login   │    │ message  │          │
│  └──────────┘    └──────────┘    └──────────┘          │
│       ↓              ↓              ↓                   │
│  Обработчик события → onMessage → Обработка → msg.say() │
└─────────────────────────────────────────────────────────┘
```

**Характеристики:**
- SDK-подход, управление событиями
- Слушание сообщений через `bot.on('message')`
- Прямой вызов `msg.say()` для отправки сообщений

### 1.2 Новая архитектура (awada-server / qiweapi)

```
┌─────────────────────────────────────────────────────────────────┐
│                    HTTP API qiweapi                              │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐        │
│  │ Установка адреса обратного вызова │    │ Отправка сообщения по обратному вызову │    │ API отправки сообщения  │        │
│  └──────────────┘    └──────────────┘    └──────────────┘        │
│         ↓                  ↓                    ↓                 │
│  Webhook-интерфейс → Сервис обработки сообщений → Redis Stream → Обработка Bot → Отправка API   │
└─────────────────────────────────────────────────────────────────┘
```

**Характеристики:**
- Режим API HTTP + Webhook-обратный вызов
- Получение сообщений через обратный вызов адреса
- Управление очередью сообщений с использованием Redis Streams
- Принимает архитектуру с управлением событиями Inbound/Outbound

## 2. Процесс получения сообщений

### 2.1 Получение обратного вызова (Webhook)

**Вход:** `POST /webhook`

```typescript
Платформа qiweapi
  ↓ HTTP POST
Маршрутизатор Webhook (src/routes/webhook.ts)
  ↓ Разбор данных обратного вызова
handleRawMessage()
  ↓ Распределение по типу cmd
```

**Типы обратного вызова (cmd)：**
- `11016`: Сообщение об изменении состояния учетной записи
- `20000`: Асинхронное сообщение API
- `15500`: Системные сообщения WeChat (заявки на добавление в друзья, изменения участников группы и т.д.)
  - `msgType=2357/2132`: Уведомление о заявке на добавление в друзья → Вызов `onFriendApply()`
  - `msgType=1002/1003/1005`: Изменения участников группы → TODO
- `15000`: Обычные сообщения WeChat (текст, изображение, файл, голос и т.д.)

### 2.2 Разбор сообщений

**Разбор обычных сообщений** (cmd=15000)：

```typescript
parseMessage(rawMsg)
  ↓
Извлечение полей：
  - content: Текстовое содержимое
  - atList: Список @
  - fromRoomId: ID группы (для сообщений в группе)
  - msgType: Тип сообщения
  - senderId: ID отправителя
  ↓
Стандартный формат CallbackMessage
```

## 3. Процесс обработки сообщений

### 3.1 Точка входа в обработку

**Файл**：`src/services/message/index.ts`

**Функция**：`handleMessage(message: CallbackMessage)`

### 3.2 Блок-схема полного процесса обработки

```
┌─────────────────────────────────────────────────────────────┐
│                   Сообщение доходит до handleMessage()                    │
└─────────────────────────────────────────────────────────────┘
                             ↓
         ┌───────────────────┴───────────────────┐
         │                                       │
     cmd === 15000?                         Другие cmd
         │                                       │
        Да                                      Нет
         │                                  Возврат без обработки
         ↓
┌───────────────────────────────────────────────────────────────┐
│           Проверка немедленно реагирующих режиссерских инструкций                                │
│  isImmediateDirectorCommand()                                 │
│    - /ding: И私聊/групповой чат можно использовать     │
│    - /start: Групповой чат + @机器人                                   │
│    - /stop: Групповой чат + @机器人                                    │
└───────────────────────────────────────────────────────────────┘
         ↓
    Запрос немедленного отклика?
         │
     ┌───┴───┐
   Да      Нет
     │       │
     │       ↓
     │   ┌─────────────────────────────────────────────┐
     │   │        Проверка прав доступа в группе                        │
     │   │  - Является ли это групповым сообщением?                              │
     │   │  - Упоминается ли бот?                          │
     │   │  - Включены ли права в группе?                        │
     │   └─────────────────────────────────────────────┘
     │           ↓
     │       Проверка прав пройдена?
     │           │
     │       ┌───┴───┐
     │      Да      Нет
     │       │       │
     │       │       └─→ Отправка сообщения о недостатке прав, возврат
     │       │
     │       ↓
     │   ┌─────────────────────────────────────────────┐
     │   │        Преобразование сообщения в Payload                    │
     │   │  - Текстовое сообщение: [{type: "text", text: "..."}] │
     │   │  - Мультимедиа: [{type: "image", ...}, ...]    │
     │   └─────────────────────────────────────────────┘
     │           ↓
     │   ┌─────────────────────────────────────────────┐
     │   │        Публикация в Redis Inbound Stream           │
     │   │  - Построение InboundEvent                        │
     │   │  - Запись в awada:events:inbound:{lane}         │
     │   └─────────────────────────────────────────────┘
     │
     └─→ Обработка инструкции и возврат
```

### 3.3 Подробные шаги обработки

#### Шаг 1: Проверка типа сообщения

```typescript
if (message.cmd !== 15000) {
  return { handled: false }; // Обрабатывать только обычные сообщения
}
```

#### Шаг 2: Проверка немедленно реагирующих инструкций

**Поддерживаемые инструкции：**
- `/ding`: Тестовая инструкция, можно использовать в частном чате или групповом чате
- `/start`: Включить права в группе (групповой чат + @机器人）
- `/stop`: Выключить права в группе (групповой чат + @机器人）

**Логика обработки：**
```typescript
// Инструкция /start
if (content === '/start' && message.fromRoomId) {
  1. Вызов интерфейса информации о группе для получения информации о группе
  2. Сохранение информации о группе в room_users.json
  3. Отправка ответного сообщения
  4. Возврат handled: true
}

// Инструкция /stop
if (content === '/stop' && message.fromRoomId) {
  1. Удаление информации о группе из room_users.json
  2. Отправка ответного сообщения
  3. Возврат handled: true
}
```

#### Шаг 3: Проверка прав в группе

**Условия проверки：**
- Должно быть групповое сообщение (существует `fromRoomId` и не равен 0）
- Должно быть упоминание бота (в `atList` должен быть userId бота）

**Определение прав：**
```typescript
if (isGroupMessage && isMentioned) {
  if (!isRoomEnabled(roomId)) {
    // Права не включены
    - Отправка сообщения о недостатке прав
    - Возврат handled: true, immediateResponse: 'no_permission'
  }
}
```

**Источник данных прав：**
- Группы, присутствующие в файле `room_users.json` = права включены
- Группы, отсутствующие в файле = права не включены

#### Шаг 4: Преобразование сообщений

**Текстовые сообщения：**
```typescript
payload = [{ type: 'text', text: message.content }]
```

**Мультимедийные сообщения**（изображение, файл, голос）：
```typescript
payload = [
  { type: 'text', text: '...' },      // Необязательный текст
  { type: 'image', file_url: '...' }, // Изображение
  { type: 'file', file_id: '...' },   // Файл
  { type: 'audio', file_id: '...' }   // Голос
]
```

#### Шаг 5: Публикация в Redis

**Построение InboundEvent：**
```typescript
{
  schema_version: 1,
  event_id: "evt_xxx",
  type: "MESSAGE_NEW",
  timestamp: 1234567890,
  meta: {
    platform: "wechat",
    tenant_id: "...",
    channel_id: "...", // ID группы или "0"（частный чат）
    lane: "linfen",
    user_id_external: "...",
    session_id: "...",
    source_message_id: "..."
  },
  payload: [...] // Массив ContentObject[]
}
```

**Публикация в Stream：**
- Ключ Stream：`awada:events:inbound:{lane}`
- Автоматическое управление `session_seq`（гарантия порядка）

## 4. Процесс обработки Bot ( downstream）

### 4.1 Bot потребляет Inbound Stream

```
Экземпляр Bot
  ↓
Подписка на Redis Stream: awada:events:inbound:{lane}
  ↓
XREADGROUP потребление сообщений
  ↓
Проверка уникальности（event_id）
  ↓
Блокировка сеанса + проверка номеров последовательностей
  ↓
Обработка (AI-ответы, вызов инструментов и т.д.)
  ↓
Генерация ответного сообщения
  ↓
Публикация OutboundEvent в Redis
```

### 4.2 Формат OutboundEvent

```typescript
{
  schema_version: 1,
  event_id: "evt_resp_xxx",
  reply_to_event_id: "evt_xxx", // Ассоциированное входящее событие
  type: "REPLY_MESSAGE",
  target: {
    platform: "wechat",
    user_id_external: "...",
    channel_id: "...", // ID группы или "0"（частный чат）
    conversation_id: "..."
  },
  payload: [
    { type: 'text', text: '...' },
    { type: 'image', file_url: '...' }
  ]
```

## 5. Процесс отправки сообщений

### 5.1 Потребление Outbound

**Файл**：`src/services/outbound/index.ts`

**Процесс：**
```
Server подписка: awada:events:outbound:{lane}
  ↓
XREADGROUP потребление OutboundEvent
  ↓
Проверка уникальности
  ↓
Распределение по platform
  ↓
Отправка сообщений в порядке массива payload
```

### 5.2 Порядок отправки сообщений

**Важно**：Сообщения в массиве `payload` **должны отправляться в порядке следования**

```typescript
for (let i = 0; i < payload.length; i++) {
  const obj = payload[i];
  
  switch (obj.type) {
    case 'text':
      await sendMessage(toId, obj.text, ...);
      break;
    case 'image':
      await sendImageMsg(toId, obj.file_url, ...);
      break;
    case 'file':
      await sendFileMsg(toId, {...}, ...);
      break;
    case 'audio':
      // TODO: Отправка голосовых сообщений
      break;
  }
}
```

### 5.3 Сопоставление интерфейсов отправки

| Тип payload | Интерфейс qiweapi | Описание |
|-------------|-------------|------|
| `text` | `/msg/sendText` | Отправка чистого текстового сообщения |
| `image` | `/msg/sendImage` | Отправка изображения в формате JPG |
| `file` | `/msg/sendFile` | Отправка файлового сообщения |
| `audio` | `/msg/sendVoice` | Отправка голосового сообщения в формате AMR |

## 6. Механизм управления правами доступа

### 6.1 Управление правами в группе

**Включение прав：**
- Режиссер упоминает бота в группе и отправляет `/start`
- Система вызывает `/room/batchGetRoomDetail` для получения информации о группе
- Сохранение в `database/wechatyui/room_users.json`

**Выключение прав：**
- Режиссер упоминает бота в группе и отправляет `/stop`
- Удаление информации о группе из `room_users.json`

**Проверка прав：**
- Групповое сообщение и упоминание бота → Проверка, присутствует ли группа в `room_users.json`
- Права не включены → Отказ от обработки, отправка сообщения с подсказкой
- Права включены → Нормальная обработка

### 6.2 Права в частном чате

- **Не подпадает под ограничение прав в группе**：Частные сообщения обрабатываются напрямую, без проверки прав
- Пользователь может отправить частное сообщение после добавления бота в друзья

### 6.3 Права режиссера

**Определение режиссера：**
- Настроено в массиве `directors` в файле `config.json`
- Режиссеры могут отправлять инструкции（`/ding`, `/start`, `/stop`）

**Права инструкций：**
- `/ding`: Можно использовать в частном чате и групповом чате
- `/start`, `/stop`: Только в групповом чате и с упоминанием бота

### 6.4 Обработка заявок на добавление в друзья

**Точка входа в обработку**：`src/services/friendship/index.ts`

**Условия срабатывания：**
- Системное сообщение（cmd=15500）
- Тип сообщения：`SystemMsgType.FRIEND_APPLY` (2357) или `SystemMsgType.FRIEND_APPLY_2` (2132)

**Процесс обработки：**

```
┌─────────────────────────────────────────────────────────────┐
│           Получен обратный вызов заявки на добавление в друзья (FriendApplyCallback)               │
└─────────────────────────────────────────────────────────────┘
                         ↓
         ┌───────────────────────────────┐
         │    Проверка прав пользователя                │
         │  - Находится ли пользователь в списке режиссеров?          │
         │  - Находится ли пользователь в списке участников группы с правами?  │
         └───────────────────────────────┘
                         ↓
             ┌───────────┴───────────┐
           Да                      Нет
             │                       │
             ↓                       ↓
     ┌───────────────┐       ┌───────────────┐
     │ Автоматически согласиться с заявлением   │       │ Не согласиться автоматически     │
     │ 1. Получить corpId  │       │ Записать в журнал       │
     │ 2. Вызвать API согласия │       └───────────────┘
     │ 3. Сохранить сообщение приветствия  │
     │    (опционально)  │
     └───────────────┘
             ↓
     ┌───────────────┐
     │ Отправить приветствие     │
     │ (person_speech│
     │  .welcome)     │
     └───────────────┘
```

**Логика проверки прав：**
```typescript
// Проверка, находится ли пользователь в списке разрешенных
function hasPermission(userId: string): boolean {
  // 1. Проверка, является ли пользователь режиссером
  if (directors.includes(userId)) return true;
  
  // 2. Проверка, находится ли пользователь в списке участников группы с правами
  const allMemberIds = roomUsers.reduce((acc, entry) => {
    return [...acc, ...entry.room.memberIdList];
  }, []);
  
  return allMemberIds.includes(userId);
}
```

**Процесс автоматического согласия：**
1. Вызов `checkLogin(guid)` для получения `corpId` текущего вошедшего пользователя
2. Вызов `agreeContact(userId, corpId, guid)` для согласия с заявлением на добавление в друзья
3. Сохранение приветственного сообщения в `HelloMap` (если оно существует）
4. Отправка приветственного сообщения：`person_speech.welcome` (считывается из `config.json`）

**Хранение приветственного сообщения：**
- Используется объект `HelloMap` для хранения：`userId -> helloMessage`
- Можно получить через `Hello.get(userId)`
- Можно добавить через `Hello.add(userId, message)`
- Можно удалить через `Hello.remove(userId)`

**Реализация-ссылка：**
- Проект wechaty：`service/bot/friendship.ts`
- awada-server：`src/services/friendship/index.ts`

## 7. Обработка типов сообщений

### 7.1 Поддерживаемые типы сообщений

| msgType | Описание | Способ обработки |
|---------|------|---------|
| 0, 2 | Текст | Прямое извлечение `content` |
| 7, 14 | Изображение企微 | Извлечение `fileId` 或 `fileHttpUrl` |
| 101 | Изображение个微 | Извлечение `fileBigHttpUrl` / `fileMiddleHttpUrl` |
| 15, 20 | Файл企微 | Извлечение `fileId` 或 `fileHttpUrl` |
| 102 | Файл个微 | Скачивание и преобразование в `cloudUrl` |
| 16 | Голосовое сообщение | Извлечение `fileId` или `fileHttpUrl` |

### 7.2 Правила преобразования сообщений

**Текстовые сообщения：**
```typescript
payload = [{ type: 'text', text: message.content }]
```

**Мультимедийные сообщения：**
```typescript
payload = [
  { type: 'text', text: '...' },        // Необязательный
  { type: 'image', file_url: '...' },   // Изображение
  { type: 'file', file_id: '...' },     // Файл
  { type: 'audio', file_id: '...' }     // Голос
]
```

**Ограничения：**
- В одном массиве payload может быть максимум 1 элемент типа `text`
- Можно включать несколько элементов `file`, `image`, `audio`
- При наличии `text` должен присутствовать хотя бы один элемент `file` или `image`

## 8. Ключевые различия в сопоставлении

### 8.1 wechaty vs awada-server

| Пункт функциональности | wechaty | awada-server |
|--------|---------|--------------|
| **Получение сообщений** | SDK-событие, слушание | Webhook HTTP-обратный вызов |
| **Отправка сообщений** | `msg.say()` | Вызов API HTTP |
| **Права в группе** | `WechatyUi.getPermissionRoom()` | Файл `room_users.json` |
| **@-проверка** | `msg.mentionSelf()` | Разбор массива `atList` |
| **Очередь сообщений** | Отсутствует (прямая обработка） | Redis Streams |
| **Управление параллелизмом** | Отсутствует | Блокировка сеанса + номер последовательности |
| **Формат сообщений** | Объект wechaty Message | Стандартизированный массив Payload |

### 8.2 Отличия в процессе обработки

**wechaty**：
```
Получение сообщения → onMessage → Фильтрация → Обработка → msg.say()
```

**awada-server**：
```
Получение сообщения → Webhook → Разбор → Проверка прав → Преобразование → Redis → Обработка Bot → Redis → Отправка API
```

## 11. Обработка ошибок

### 11.1 Ошибка обработки сообщений

- Запись сообщения об ошибке
- Не выбрасывать исключение, чтобы не повлиять на обработку других сообщений
- Возврат `handled: false`

### 11.2 Ошибка отправки

- Запись сообщения об ошибке
- Продолжение отправки последующих сообщений (не прерывание）
- Поддержка механизма повторных попыток (через механизмpending Redis Streams）

### 11.3 Ошибка проверки прав

- Отправка подсказывающего сообщения пользователю
- Возврат `handled: true, immediateResponse: 'no_permission'`

## 12. Оптимизация производительности

### 12.1 Ленивая загрузка

- Экземпляры EventProducer, ConversationManager и т.д. используют ленивую загрузку
- Избежание инициализации Redis при загрузке модулей (Redis может быть еще не инициализирован）

### 12.2 Кэширование

- Кэширование userId бота (избежание повторных вызовов API）
- Кэширование Conversation ID (хранение в Redis）

### 12.3 Пакетная обработка

- Redis Streams поддерживает пакетное потребление
- Поддержка пакетных операций Pipeline

## 13. Мониторинг и логирование

### 13.1 Ключевые точки логирования

- Получение сообщения：`[Webhook] Получен обратный вызов`
- Обработка сообщения：`[MessageService] Сообщение уже опубликовано в Redis`
- Проверка прав：`[Message] ⚠️ Права в группе не включены`
- Обработка инструкций：`[Message] Обработка инструкции /start`
- Отправка сообщения：`[Outbound] ✅ Завершена отправка N сообщений`

### 13.2 Показатели мониторинга

- lag Inbound/Outbound（задержка сообщений）
- Количество pending（ожидающие сообщения）
- Успешный/неуспешный показатели
- P95/P99 затраченное время на обработку
